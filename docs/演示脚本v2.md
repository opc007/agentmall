## 0. 演示前必读（3 条，别省）

0. **先彩排**（最高优先级，三条命令，**顺序不能反**）：
   ```bash
   ./scripts/start_demo.sh --check  # ① 八套测试 + 真跑一遍 9 步，逐步打印话术
   ./scripts/reset_demo.sh          # ② 验完清库（彩排会留下一笔单，带它上台会掉分）
   ./scripts/start_demo.sh          # ③ 重新起服务，正式开演
   ```
   ①的输出在 `/tmp/agentmall_rehearse.log`。
   只想看话术不跑测试：`.venv/bin/python scripts/rehearse.py --isolated`（不碰演示库）

1. **开演声明**（一定要说出口）：
   > 「先说明：商品是我们的**演示商品库**，支付是**模拟支付网关**，全程不发生任何真实交易，
   > 也不会有任何自动扣款。」

2. **合规范式**（被问到时反复强调，这是本项目最大的设计主张）：
   > 「我们采用 Anthropic 官方 commerce-agents 蓝图的 **checkout hands off** 范式：
   > **下单是智能体的事，付钱永远是用户的事**。智能体只建单，模型碰不到钱。」

3. **诚实边界**：不接 1688 真实 API（公开市场价格的演示商品库 + 爬虫已就绪）、
   不接真实支付网关。**不要说「已接 1688」**，追问两句会穿帮。

## 2. 角色一：用户智能体（主戏，7 步）

完整流程见 `docs/路演Demo流程.md`，此处给可直接照念的话术。

### 步骤 1–2：注册 + 拿接入点
浏览器打开 http://127.0.0.1:8000 → 注册（用户名+密码）→ 登录 → 进「个人中心」。

> **话术**：「用户注册完，系统给他一个**专属的 MCP 接入点**——一个 URL 加一个密钥，
> 复制粘贴就能配给自己的 AI 智能体。**每个用户的密钥独立，智能体之间天然隔离。**」

### 步骤 3–5：把接入点配给 AI，说人话
对智能体（workbuddy）说：

> 「帮我找最便宜的抽纸，30 元以内，送到广西南宁市朝阳广场。」

**期望看到**：
1. 智能体调 `search_products(keyword="纸巾", max_price=30)` → 返回按价格升序的商品列表
2. 智能体回你：「最便宜的是 **洁云 雅致生活 抽纸 3层100抽*27包，¥13.90**。
   我给你建单，地址广西南宁市朝阳广场，可以吗？」
3. 你确认后，智能体调 `create_order(product_id="P112", quantity=2, address="广西南宁市朝阳广场")`

**期望返回**（真实结构）：
```json
{
  "order_id": "AM517B770461",     // AM + 10 位大写
  "total": 27.8,                   // 单价 × 数量
  "status": "待支付",
  "pay_url": "http://127.0.0.1:8000/pay/AM517B770461?t=demo_...",
  "is_demo": true
}
```

> **话术**：「智能体现在完成的是**建单**——它算好了价、锁了库存、给了订单号。
> 但它**没有、也不能**扣你的钱。付钱这一步在你自己这边。」

### 步骤 6：网页订单列表 → 去支付
切回网页 → 「我的订单」看到刚生成的订单，状态**待支付** → 点「去支付」。

**期望看到**：模拟收银台页，顶部橙条明示「⚠️ 演示环境 · 模拟支付 · 不发生任何真实资金交易」，
显示订单号 / 金额 / 商品明细 / **二维码**（二维码内容就是这个收银台页的 URL）。

> **话术**：「二维码扫出来就是这个收银台页。注意——**点确认的是你，不���智能体。**
> 这就是 checkout hands off：模型永远碰不到钱。」

### 步骤 7：确认支付
点「确认支付 ¥27.80」→ 订单状态变为 **已完成**。

> **话术**：「演示订单标记 `is_demo=1`，支付后直接置为已完成、**不触发发货**——
> 因为我们还没接 1688，没有真实履约。真实订单走的是『待发货 → 待收货』，
> 商户智能体发货那条链路是通的，可以现场演。」

### 步骤 7b：可现场演的替代路径（想演商户发货时用）
用 `is_demo=False` 建一单（商户侧演示见 §4），状态会是「待发货」，
商户调用 `merchant_fulfill_order` 后变成「待收货」。

## 3. 角色二：商户智能体（5 个 tool）

用商户 M001 的 key 配一个 AI 客户端（或让同一个 AI 切换身份）。

| tool | 参数 | 干什么 |
|---|---|---|
| `merchant_publish_product` | name, category, price, stock, unit, specs | 上架，**进待审核** |
| `merchant_update_product` | product_id, price, stock, on_sale | 改价/改库存/上下架 |
| `merchant_list_products` | — | 自己全部商品（含待审核/下架） |
| `merchant_list_orders` | status | 自己店铺订单（**地址已脱敏**） |
| `merchant_fulfill_order` | order_id, tracking_no | 发货 → 待收货 |

**演示顺序**（这 5 个串成一条业务线）：

1. **说**：「上架一个商品，洁柔手帕纸，19.9 元一包，先备 200 库存。」
   → `merchant_publish_product(...)` 返回 `{"status": "待审核"}`
   → **立刻用用户搜索这个商品，搜不到**（这是审核流的证据，务必演）

2. **切管理员**（见 §4）审核通过 → 切回用户搜索，**现在能搜到了**

3. **说**：「把这个商品降到 18.9。」
   → `merchant_update_product(product_id=..., price=18.9)`

4. **说**：「我店铺现在有哪些订单？」
   → `merchant_list_orders()`，**注意地址只显示到市级**（`广西南宁市`，看不到朝阳广场）
   > **话术**：「合规红线：**商户只能看自己店铺的订单**，而且**买家地址脱敏到市级**，
   > 看不到门牌号。不同角色看到的数据是不同的，这是硬隔离。」

5. **说**：「给订单 AMxxxx 发货，运单号 SF123456789。」
   → `merchant_fulfill_order(...)` → 状态变「待收货」

6. **越权演示（强烈建议演）**：拿 M001 的 key 去改 M002 的商品
   → 返回 `{"error": "只能操作本商户的商品", "denied": true}`，**并记入审计日志**
   > **话术**：「商户 A 碰不了商户 B 的数据。这是代码层强制的，不是靠提示词约束。」

## 4. 角色三：管理员智能体（5 个 tool + 网页后台）

打开 http://127.0.0.1:8002，用 `ak_demo_admin_secret` 登录。

| tool | 参数 | 干什么 |
|---|---|---|
| `admin_review_product` | product_id, approve, reason | 审核上架（**驳回 reason 必填**） |
| `admin_takedown_product` | product_id, reason | 下架（**reason 必填**），记审计 |
| `admin_list_merchants` | — | 商户列表（商品数/订单数） |
| `admin_stats` | — | 看板：订单数/GMV/用户数/商户数/商品数/待审核数 |
| `admin_audit_log` | limit | 审计日志（只读） |

**演示顺序**（接着 §3 的待审核商品往下走）：

1. **网页后台「看板」**：
   > **话术**：「切到管理侧——**同一笔刚才用户下的单，平台这边实时就看到了**。
   > 订单数、GMV、用户数都在这儿。这就是一个电商平台该有的全域视角。」

2. **审核商品**（如果 §3 演了上架）：待审核列表点「通过」
   > **话术**：「商户上架不能直接卖，**必须过平台审核**。这是内容治理的风控闸门。」

3. **下架商品**：在「商品治理」页填原因下架
   > **话术**：「管理员下架必须**填原因**，而且**写进审计日志**。
   > 数据库层还挂了触发器，审计日志**禁止删改**——不是靠约定，是靠数据库。」

4. **切回用户搜索**：刚才被下架的商品**搜不到了**
   > 「这就是管理员动作的**实时生效**。」

5. **「审计日志」页**：
   > **话术**：「每一次越权拦截、每一次下架、每一次审核，who / when / what 全留痕。」

## 5. 三角色联动的完整故事线（如果时间够，演这个）

```
商户上架商品（待审核）
   → 管理员审核通过
      → 用户搜到、智能体建单（扣库存）
         → 用户自己在网页扫码支付
            → 商户看到订单（地址脱敏）并发货
               → 管理员看板订单数 +1、GMV 增长
                  → 审计日志全程留痕
```

一句话总结（收尾用）：
> 「**三权分立**——买的人、卖的人、管平台的人，看到的数据和能做的操作完全不同。
> 智能体只是这些角色里的**一双手**，不是全部。」

## 6. 兜底：如果现场出问题了

| 情况 | 怎么办 |
|---|---|
| 智能体连不上 MCP | 确认 `/whoami` 有返回；检查 Bearer key 是不是用户自己的 |
| 搜不到刚上架的商品 | **这是对的**——待审核商品用户不可见，正好用来演示审核流 |
| 支付页打不开 | 看 `AGENTMALL_PUBLIC_URL` 有没有设成实际访问的地址 |
| 想重置演示数据 | `./scripts/reset_demo.sh`（自动备份旧库到 `/tmp`，比手删文件安全） |
| 看板 GMV 没涨 | **别用「口径问题」圆过去**，订单已「已完成」就该计入 GMV。当众说「这块还在调」比数字对不上体面 |
| 只想快速看全貌 | `./scripts/start_demo.sh --check` 一键起服务并跑完八套测试 + 路演彩排 |
| 想看每步完整话术 | `.venv/bin/python scripts/rehearse.py`（或看 `/tmp/agentmall_rehearse.log`） |

## 7. 投资方常见提问 · 标准答法

> **被问到「你们接了 1688 吗」——这是最关键的一问，照实说。**

**Q：接了 1688 吗？**
> 「还没接。今晚跑通的是**架构和全链路**——商品用的是我们基于**公开市场价格**整理的
> 演示商品库，59 个 SKU，五类日用品。爬虫脚本已经写好、能在联网环境直接跑，
> **Phase 2 接 1688 官方开放平台**。选型我们已经做完调研了：`docs/货源接口选型.md`。
> 关键一条是**必须用分销价接口 `alibaba.agent.price.get`**，
> 拿普通商品接口的批发价会直接亏本。」

**Q：支付是真的吗？会不会自动扣款？**
> 「是模拟网关，真网关接口已经预留好了，换个实现类就行。
> **我们绝不会做自动扣款**——这不只是技术选择，是合规红线。
> 中国支付清算协会有《智能体支付应用自律公约》，第一阶段就是『辅助支付』：
> 智能体下单，用户自己付。**模型碰不到钱**，这是设计出来的，不是承诺。」

**Q：智能体会不会乱花钱？**
> 「用户侧智能体**只有 4 个工具**：搜索、看详情、建单、查单。
> **改价、改库存、上下架全部没有**——我们用 CI 测试在代码层卡死，
> 源码里就不存在这些方法，不是靠提示词约束模型。商户和管理员的写操作则全部记审计日志。」

**Q：怎么防超卖？**
> 「下单时校验 `quantity <= stock`，扣库存和建单在**同一个数据库事务**里完成，
> 并发的抢单不会超卖。超过库存直接返回『库存不足』。」

**Q：三个角色怎么隔离？**
> 「每个请求带一个 API key，key 决定角色，**服务端只给这个角色注册它能用的工具**。
> 用户 key 只能看到 4 个工具，管理员 5 个，商户 5 个。
> 拿用户 key 调管理员接口会被直接拒绝，并且**记进审计日志**——刚才可以现场演。」

**Q：数据量多大？**
> 「演示阶段 59 个 SKU。真实数据在 Phase 2 走定时批量同步，1688 商品搜索接口
> 单次最多返回 200 条。」

**Q：这东西现在能商用吗？**
> 「不能，还差三块：① 接 1688 真实货源；② 接真实支付网关并完成合规评估报备；
> ③ 把演示级的登录态换成正式会话。这三块都在路线图上，架构口子已经留好了。」
